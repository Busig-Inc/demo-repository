# Архитектура MVP

## Три слоя

```
 content/  ──данные──▶  ui/  ──эффекты──▶  engine/
 (что сказать,          (экраны,           (состояние, правила,
  какие окна,            окна, области)     финал, разбор)
  какие последствия)          ▲                  │
                              └────состояние─────┘
```

- **`src/engine/`** — чистые функции без DOM, их проверяют тесты.
  - `state.js`: состояние игры и `apply(state, effect)`. Неизвестный эффект или недопустимое значение вызывает ошибку.
  - `rules.js`: какие планы открыты (`planAvailability`), смета (`ledger`), какой финал наступил (`resolveFinal`), следующий шаг после подписи (`stepAfterSign`), куда можно перейти по адресу (`guardRoute`).
  - `review.js`: путь игрока, карта возможностей, цепочки причин, альтернативы и пересчёт «изменить одно решение».
  - `save.js`: автосохранение в `localStorage` (ключ `afg.insulin`). Сохранение другой версии сбрасывается.
- **`src/content/`** — данные. Сюда не нужен программист.
  - `texts.data.js` и `texts.ru.js`: словарь интерфейса.
  - `missions/insulin/mission.data.js`: тексты и окна сцен из дизайн-пакета без изменений.
  - `missions/insulin/scenes.js`: поведение сцен: `effect`, `when`, `next`.
  - `plans.js`, `finals.js`, `review.js`, `places.js`, `presets.js`.
- **`src/ui/`** — экраны.
  - `router.js`: hash-адреса `#/start`, `#/world`, `#/city`, `#/scene/s1`, `#/council`, `#/final`, `#/review`.
  - `store.js`: единственное место, где живёт состояние.
  - `screens/`: старт, карта мира, карта Торонто, сцена, совет, финал, разбор.
  - `windows/`: типы окон действий, по файлу на тип.
  - `areas.js`: папка, смета, календарь.
  - `styles.js`: подключает CSS пакета под каждый экран.

## Поток одного действия

1. Игрок нажимает действие в сцене. Открывается окно нужного типа (`windows/<тип>.js`).
2. Окно сообщает результат `outcome = { ok, value }`. Например, для `pack` это номера выбранных карточек.
3. Сцена берёт `effect(outcome)` из данных миссии и отправляет эффекты в `store.dispatch`.
4. Движок применяет эффекты и пишет запись в журнал. Состояние сохраняется.
5. Три области перерисовываются из `ledger(state)`. Финал и разбор потом строятся по тому же журналу.

## Правила, которые держит движок

- Одну единицу нельзя потратить дважды, остаток не уходит в минус.
- Подписать можно только открытый план. N требует отдельного разрешения на риск.
- Подпись необратима. После неё места до совета закрыты, а «назад» в браузере ведёт на текущий шаг.
- Финал наступает только после последнего шага маршрута.
- Перед подписью и перед S9 сохраняются снимки состояния. Из них разбор пересчитывает альтернативы и даёт «Пройти отсюда».

## Почему стили подключаются под экран

Страницы дизайн-пакета (`экран_старт.html`, `экран_мир.html`, `экран_город.html`, `экран_план.html`) самодостаточны, и классы вроде `.stage`, `.drawer`, `.areas` в них определены по-разному. Поэтому `ui/styles.js` подключает для каждого экрана тот же набор CSS, что был у его страницы в пакете. Новые стили MVP лежат только в `styles/app.css` и используют токены из `tokens.css`.

## Проверки

- `npm test`: движок, правила по таблице сценария «Как устроены расчёты», разбор и целостность данных. В данных проверяется, что каждый вариант каждого окна даёт допустимый эффект, переходы ведут на существующие экраны, а у документов стоят метки достоверности.
- `npm run e2e`: полный проход маршрутов H, L (контроль и исследование), N, W, трёх быстрых входов и перезагрузки после подписи, на экранах 1440×900 и 1280×720, без ошибок в консоли.
